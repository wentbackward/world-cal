Alternative: in-grid cancel aborts — rejected as inconsistent with the spec sentence. Pinned by a jsdom test asserting the in-grid cancel commits.
- 2026-11-21 — setPointerCapture is guarded (try/catch) — jsdom and older browsers lack it; window-level listeners are the primary outside-grid path. Alternative: hard-require capture — rejected (breaks jsdom and fall-backs).

- 2026-11-21 — a drag is bound to its initiating pointerId for the whole drag: pointerdown/move/up/cancel from any other pointer are ignored (including pointerdowns flagged isPrimary), only the initiating pointer's release commits, and window pointerup/pointercancel events must match the active pointerId — a second finger tap mid-drag no longer steals the drag (previously its release committed the wrong hour-10 tap over the in-progress region). Alternative: guard only on isPrimary — rejected; the flag does not identify the initiating pointer, so a second pointer can still reset state.
- 2026-11-21 — the window keydown Escape handler ignores events already defaultPrevented by an earlier listener and events whose target is an input/textarea — an Escape aimed at an input (mid-drag, typing) or an already-handled Escape cancels neither the drag nor the overlay; it is the input/handler that owns it. - 2026-11-21 — `getLocalHour` stays on its own h24 + normalize path, not on `getOffsetMs` (documented deviation from §2's routing bullet). Alternative: derive the local hour from `getOffsetMs` — declined; see below.
  Built on `Intl.DateTimeFormat().formatToParts` with `hourCycle: "h24"` (midnight emits hour "24" in some ICUs, "00" in others) and normalizes
  `24 → 0`, rather than the previous `toLocaleString(..., hour12: false)` + parse — the spec pins the *normalized 0–23* contract but not the cycle; h24
  makes the hour-24 normalization load-bearing in the ICUs that emit 24 (the `hour12: false` behaviour that emits 24 is environment-dependent, so the
  old path would silently skip normalization somewhere). The test pins the real midnight case. Alternative: keep `hour12: false` and normalize anyway —
  rejected, the 24 emission is exactly what is unreliable.
  §2's routing bullet was narrowed per ticket #14 to name only `getOffsetLabel`, `sortTimezonesByOffset` (if kept) and `createDateAtTime` as routed
  through `getOffsetMs`; `getLocalHour` is named as the deliberate exception there. Deriving from `getOffsetMs` is declined: the acceptance-criteria
  list — the authoritative contract — only requires `getOffsetLabel` and `createDateAtTime` to route through `getOffsetMs`, and duplicating the
  ms-offset subtraction to print an hour would add redundant math for no gain. A fixed local-hour path is the deliberate, documented deviation; §2's
  routing bullet is not silently taken as covering it.
- 2026-11-21 — `getOffsetLabel` derives hours/minutes from `getOffsetMs` in minutes (`Math.round(ms / 60_000)`, `h = floor(m/60)`, `m = m % 60`), not from whole hours — the half-hour and quarter-hour zones (Kolkata +5:30, Kathmandu +5:45) round cleanly to whole hours in the old hour-based math and the existing tests pass either way; minutes arithmetic is the exact source of truth the spec requires and avoids float rounding drift. Alternative: keep `getTzOffset`-style whole-hour math — rejected; hours are the fragile unit the ticket removes.
- 2026-11-21 — `getOffsetMs` floors the reference instant to whole seconds (`Math.floor(date.getTime() / 1000) * 1000`) before subtracting — `formatToParts` truncates to seconds, so a caller instant carrying a millisecond fraction (e.g. `12:00:00.500Z`) would otherwise leak the fraction into the result (`-14400500` instead of `-14400000`). All current callers pass whole-second instants, so impact today is theoretical; flooring is the one-line clamp that makes the published "exact" helper correct for any input. Alternative: leave the raw subtraction — rejected; the helper is now the single source of truth and should not be drift-prone.
- 2026-11-21 — `requiredPart` helper throws a named-part error in `getLocalHour` and `getOffsetMs` when formatToParts omits a part — the format guarantees the parts, so an absence is a genuine bug and should fail loudly with the part named, not silently propagate NaN into `Date.UTC` (or fall back to a wrong hour). Alternatives: non-null assertion / `?? '0'` fallback — rejected; they hide the bug.
